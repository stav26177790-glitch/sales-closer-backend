1. подключает оба репо (`stav26177790-glitch/sales-closer-backend` и

   клонирует в `/home/claude/`;
2. читает этот HANDOFF целиком (разделы 0, 0.1, 0.2 и 6 — обязательно);
3. запускает `npm test` в бэкенде — всё должно быть зелёным;

### 0.1. Как работать с владельцем

- Владелец — не программист. Пишет по-русски, работает в Safari на Mac.
  Нужны подробные пошаговые инструкции со ссылками: куда нажать, что
  вставить, что должно получиться. Терминал владелец не использует.
- Claude сам коммитит и пушит в `main` обоих репо (автодеплой: Render —
  бэкенд, Netlify — фронтенд). Перед пушем — `npm test`. Подтверждение
  владельца нужно на смысловые решения (что говорить клиенту, условия
  компании), а не на каждый коммит.
- Проверка выката: https://sales-closer-backend.onrender.com/api/health →
  `version` = первые 7 символов последнего коммита бэкенда. Из
  облачного окружения Claude Render и Supabase недоступны (прокси) —
  проверяет владелец и присылает ответ.
- SQL в базе выполняет владелец: Supabase → SQL Editor
  (https://supabase.com/dashboard/project/nvnrhtygbjnjspzuagdz/sql/new) →
  вставить → Run → «Success. No rows returned».
- Живые тесты: владелец гоняет сделку в Клоузере и присылает ответы
  (часто файлом). Claude разбирает: что хорошо, что плохо, ПОЧЕМУ (ищет
  причину в промптах/базе/коде, в т.ч. в собственных примерах), предлагает
  правку → владелец пишет «ок/применяй» → правка, тесты, пуш, инструкция
  как проверить.
- Факты о компании (гарантия, сроки, услуги) — только от владельца.
  Нельзя выдумывать; если нужно — спросить одним вопросом.
- Свои ошибки Claude признаёт прямо (так уже было: удаление
  `approved_text` сломало доработку; неверный день недели; «временное
  решение» в собственном примере → модель выдумала временную вывеску).
- Снимки тестов обновлять только при задуманном изменении поведения и
  проверять скриптом, что изменилось только ожидаемое.

### 0.2. Принципы Клоузера (что нельзя потерять)

Методология (база знаний `knowledge/`, промпты `agents/`):
- Диагностика по СОПРАНО — 5 критериев (Финансы, Потребность, Доверие,
  Полномочия/ЛПР, Срочность), статусы Подтверждено/Вероятно/Неизвестно/Риск.
- Шесть триггеров клиента (24_client_triggers.md): Прибыль, Удобство,
  Надёжность, Тщеславие, Новизна, Симпатия. Триггер — только по цитате
  клиента и только тому, с кем было общение. Бюджет — это критерий
  Финансы, не триггер.
- **Всё через призму ЦЕННОСТИ для клиента (ФХВЭ):** факт о компании —
  не «мы хорошие», а результат для клиента и предвосхищение возражения.
  Каждая просьба о шаге — через выгоду адресата. Выгода контактному
  лицу — через помощь, не через страх/вину.
- Выход на ЛПР в обход контактного лица — только с его СОГЛАСИЯ
  (согласие = его ответ в истории), просьба — через пользу для него.
- Сроки считает КОД (`engine/timeline.js`), агенты берут даты только
  из `timeline`. Рабочие дни, праздники РФ, монтаж 2–3 дня. Без запаса —
  «впритык, если…»; «не успеваем» — честно, реальная дата + временная
  вывеска (даты из `timeline.temp_banner`). Ускоренного производства нет.
- Слот в производственном плане — наш процесс; ЛПР говорим, что даёт
  решение сейчас: точно в срок, цена из КП без доплат, без сравнения
  подрядчиков, договор/ОТК/гарантия. Конкурентов не ругать.
- Если менеджер раньше называл клиенту условие по срокам — касание
  честно ссылается на него.
- Запрещено: выдуманные цифры/гарантии/рейтинги (реальные условия —
  `knowledge/industry/signage.md`: гарантия 12 мес на всё, выезд
  2 рабочих дня, рейтингов/отзывов нет), «гарантированно/точно успеем»,
  давление и угрозы. Часть запретов проверяет код (`engine/phraseCheck.js`).

Архитектурные паттерны:
- 8 агентов на Claude, конфигурация в одном месте — `llm/registry.js`.
- Код — источник правды для расчётов и проверок, где модель ошибается
  (даты, запрещённые фразы, расхождения с менеджером, одобренные касания).
- Доработка: composer получает свои прошлые касания
  (`previous_composer_output`), одобренные reviewer'ом возвращаются
  дословно (`keepApprovedTouches`) — кроме касаний с запрещёнными фразами.
  Следствие: новые правила НЕ применяются к уже одобренным касаниям
  старой сделки — проверять правила на НОВОЙ сделке или прямой правкой.
- Ответы в чат — лёгкая разметка (`engine/chat.js` → `src/RichText.jsx`).

## 2. Как устроено сейчас

- `server.js` — 10 маршрутов: `/api/health`, `/api/ping-db`, `/api/deals` (GET/POST),
  `/api/deals/:id/history`, `/api/deals/:id/continue`, `/api/deals/:id/experience`,
  `/api/deals/:id/dismiss-stale`, `/api/deals/:id/timeline` (PATCH, сроки), `DELETE /api/deals/:id`.
- Миграции БД: `db/migrations/001_init.sql`, `002_deal_timeline.sql` — обе выполнены на живой базе.
- Машина состояний — папка `engine/` (точка входа `stateMachine.js`). Этапы: INIT → SOPRANO_INTERVIEW → DIAGNOSING →
  (CONFLICT_RESOLUTION) → STRATEGY_SELECTION → COMPOSING → REVIEWING → ESCALATION / FINAL_OUTPUT
  (+ LOST_DEAL, DISQUALIFICATION, MEMORY_UPDATE).
  - `engine/advance.js` — один ход: контекст, «заверши сессию», выбор обработчика этапа, запись в `deals`, очередь и защита от дублей;
  - `engine/steps/*.js` — по файлу на этап, реестр в `engine/steps/index.js`;
  - `engine/pipeline.js` — общие вызовы агентов: composer (единый вход), memory (итог), planner → diagnostic;
  - `engine/chat.js` — тексты для менеджера; `engine/intent.js` — ок/правка/вопрос/да-нет; `engine/config.js` — лимиты;
  - `engine/timeline.js` — расчёт сроков (рабочие дни, монтаж, временная вывеска);
  - `engine/phraseCheck.js` — запрещённые фразы в касаниях (поверх reviewer'а).
- Вызов агентов — папка `llm/` (точка входа `agentRunner.js`): `registry.js` — модель, температура, база знаний, кейсы, кэш каждого агента; `prompt.js` — системный промпт; `input.js` — сокращение длинного входа; `runner.js` — запрос к Claude, разбор JSON, логи стоимости.
- `agents/*.md` — промпты; `knowledge/` — 24 файла методологии (новый — `24_client_triggers.md`) + `knowledge/industry/signage.md` (факты компании для вывесок) + ~280 кейсов по 11 отраслям.
- Фронтенд — `src/App.jsx` (~700 строк: список сделок, чат, форма сделки с полями сроков, «Сроки» в шапке), `src/RichText.jsx` (разметка ответов), `src/Login.jsx`, `src/supabase.js`, `src/main.jsx` (AuthGate).

## 10. Как добавить менеджера

Регистрация в Клоузере закрыта: менеджера добавляет владелец в Supabase.
Вход у менеджера — по ссылке на почту, пароля нет.

### Один раз: настроить свой SMTP

Без этого письма доходят только участникам команды Supabase и не больше 2 в час.

1. Нужен почтовый ящик, от имени которого пойдут письма. Проще всего — Яндекс:
   Яндекс ID → Безопасность → **Пароли приложений** → создать пароль для «Почты».
2. Supabase → **Authentication → Emails → SMTP Settings** (вкладка SMTP) → **Enable Custom SMTP**:
   - Sender email: адрес этого ящика; Sender name: `Клоузер`
   - Host: `smtp.yandex.ru`, Port: `465`
   - Username: полный адрес ящика; Password: пароль приложения из п.1
   - **Save**.
3. Supabase → **Authentication → Rate Limits**: при необходимости поднять лимит писем в час (например, 30).
4. Проверка: выйти из Клоузера и войти снова — письмо должно прийти от нового отправителя.

Для рассылок с корпоративного домена вместо Яндекса подойдёт любой SMTP-сервис
(Unisender Go, Brevo, Resend и т.п.) — поля те же.

### Пригласить менеджера

1. Supabase → **Authentication → Users** → **Add user** → **Send invitation**.
2. Ввести рабочую почту менеджера → **Send invitation**.
3. Менеджер получает письмо-приглашение, нажимает ссылку — открывается Клоузер, он уже вошёл.
   Профиль менеджера (`managers`) создаётся автоматически при первом входе.
4. Дальше менеджер входит сам: адрес Клоузера → почта → «Получить ссылку для входа».

Вариант без письма-приглашения: **Add user → Create new user**, почта, галочка
**Auto Confirm User**, пароль любой (не используется) — менеджер сразу входит по ссылке
со страницы Клоузера.

Каждый менеджер видит только свои сделки.

### Отключить менеджера

Внимание: удаление пользователя **удаляет все его сделки** (каскадом).
Чтобы сохранить сделки, сначала передайте их другому менеджеру в SQL Editor:

```sql
update deals
set manager_id = 'ID_КОМУ_ПЕРЕДАТЬ'
where manager_id = 'ID_УХОДЯЩЕГО';
```

ID — колонка UID на странице Authentication → Users. После этого: Users → строка
менеджера → меню «…» → **Delete user**.
